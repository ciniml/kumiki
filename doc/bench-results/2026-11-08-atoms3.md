# ベンチマーク結果: AtomS3（2026-11-08）

- 機体: M5Stack AtomS3（ESP32-S3 rev v0.1、内蔵フラッシュ 8MB、PSRAM なし）、GC9107 128×128、SPI 40MHz
- kumiki: `firmware/kumiki-bench`（esp-hal 1.2.2、blocking、opt-level 3 + LTO、`EspSpiDmaBus` 16KiB×2）
- M5GFX: `bench/m5gfx-idf`（M5GFX 0.2.19、ESP-IDF 5.4.2、`-O2`、自動判別）
- シナリオ: [10-performance-plan.md](../10-performance-plan.md) §3。各 60 フレームの平均
- 理論上限: 128×128×16bit / 40MHz = 6.55ms（152.6fps）

| ID | 内容 | M5GFX | kumiki（DMA のみ） | kumiki（FIFO 経路） | kumiki（FIFO + EXECUTE 一括） | M5GFX 比（最終） |
|---|---|---|---|---|---|---|
| B1 | 全画面の塗りつぶし | 147.77 fps | 150.94 | 151.05 | **151.05** | **102%** |
| B2 | 全画面の転送（RGB565、無変換） | 152.32 fps | 150.89 | 151.05 | **151.05** | **99%** |
| B3 | RGB888 → RGB565 変換付き転送 | 149.25 fps | 146.07 | 147.38 | **147.49** | **99%** |
| B5 | 透過付きスプライト 32×32 ×64 | 31.28 fps | 11.41 | 21.96 | **25.15** | **80%** |
| B8 | 円 20 個 + 文字列 | 256.87 fps | 37.80 | 117.37 | **156.93** | **61%** |

## 所見

- 全画面の転送（B1〜B3）は理論上限の 97〜99% に達し、M5GFX と同等。M1 の完了条件（M5GFX の 80% 以上）を満たす。
- 小さな描画（B5、B8）は 1 回あたりの固定費が支配的。
  - esp-hal の DMA 転送を 1 回起動するのに数 µs かかるため、64 バイト以下は SPI の W レジスタ（FIFO）から直接送る経路（`fifo-esp32s3` feature）を追加した。
  - ESP32-S3 では UPDATE と USR を 1 回の書き込みで指示するようにした（M5GFX の `SPI_EXECUTE` と同じ）。
- B8 は同一条件ではない。kumiki は embedded-graphics の `Circle`（1 ピクセルずつ `draw_iter`）を使い、M5GFX は `drawCircle` を使っている。どちらも「ピクセルごとにウィンドウを設定して送る」点は同じで、差は 1 回あたりのソフトウェアの処理時間にある。

## 次の改善候補

- `begin_write` の CASET/RASET/RAMWR を、D/C の切り替えをまたいでまとめて送る（コマンドのたびに完了を待つ回数を減らす）。
- `draw_iter` で縦方向の連続（円の左右の辺など）もまとめる。または、まとめて描く図形を Sprite 経由にする。
- `push_keyed` の透過ランの走査を、行単位の SIMD 風比較にする。
